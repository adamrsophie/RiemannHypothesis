How to

Verify it yourself

A formal proof is only as good as the check that was run on it. This page explains how to build the project, how to confirm it uses no extra axioms, and what the current verification status is.

A text search is a smell test, not a proof. Macros, metaprograms or run_cmd blocks can in principle add declarations that never appear as text. Only the kernel checks below settle the question.

What you need

  • A 64 bit Linux or macOS machine with plenty of RAM. Expect to need tens of gigabytes of memory and disk; the project is roughly two orders of magnitude larger than Mathlib by file count.
  • elan, the Lean toolchain manager. It reads lean-toolchain and installs Lean v4.33.1 automatically.
  • git and a fast network connection for the Mathlib cache.
  • Time. A full build of 175,000 files will take many hours even with many cores.

Build

  1. Install elan. 
    curl https://elan.lean-lang.org/elan-init.sh -sSf | sh
  2. Clone. Shallow clone to save space. 
    git clone --depth 1 https://github.com/adamrsophie/RiemannHypothesis.git
cd RiemannHypothesis/lean
  3. Fetch prebuilt Mathlib. Lake downloads the pinned Mathlib commit, and the cache tool fetches its compiled files so you do not rebuild Mathlib. 
    lake exe cache get
  4. Build the final theorems. Building the Main target compiles exactly the files that the five theorems depend on. 
    lake build Main
    To build every default target instead, run lake build.

Check the axioms

A successful build shows the proofs typecheck. It does not by itself show which axioms they use. Create lean/Check.lean:

import Main

#print axioms riemannHypothesis
#print axioms riemannZeta_eq_zero_re
#print axioms LFunction_ne_zero_of_half_lt_re
#print axioms LFunction_eq_zero_re
#print axioms LFunction_eq_zero_re_of_isPrimitive

-- Confirm the statements are the expected ones
#check @riemannHypothesis
#print RiemannHypothesis

and run

lake env lean Check.lean

What a clean result looks like

'riemannHypothesis' depends on axioms: [propext, Classical.choice, Quot.sound]

These three are Lean's standard axioms, used throughout Mathlib: propositional extensionality, the axiom of choice, and quotient soundness. Any of the following in the list would mean the proof is not unconditional:

Appears in outputMeaning
sorryAxSome step was left unproved.
Any other named axiomAn assumption was added, perhaps hidden in a metaprogram.
Lean.ofReduceBool or Lean.trustCompilerSome step trusts compiled code (native_decide or similar) instead of the kernel.

Replay in an independent kernel

For the strongest check, export the compiled environment and recheck it with a separate implementation, so that a bug in Lean's own elaborator or kernel cannot hide a gap.

  • lean4checker replays the .olean files through the Lean kernel from scratch, catching environment manipulation by metaprograms.
  • lean4export writes the environment in a portable text format, which independent checkers such as nanoda (Rust) can verify.

Check the statements, not just the proofs

A perfectly checked proof of the wrong statement is worthless. The Statements page explains the four definitions. In particular, riemannHypothesis has type RiemannHypothesis, Mathlib's own definition, so the statement cannot have been weakened by the project. Confirm with #print RiemannHypothesis that it resolves to Mathlib's declaration and prints the expected body.

Reporting results

If you complete a build and an axiom check, the result is valuable to everyone. Please open an issue on the repository with your machine, build time, peak memory, and the full #print axioms output, and it will be recorded on this page.
